# plant v0.4.0: plan against the North Star

Status: draft, 2026-11-19. Work in progress, nothing built or tagged, and no
production-ready claim. The owner decides the scope in the morning decision
window; until then this is a proposal.

Update, 2026-11-21: the owner asked for a release now, so v0.4.0 ships what
is built: bet A's Lean and Kani packs, `shallow_git` and the north-star input
(REQ-015 stays draft), the lockfile gate (REQ-031) and `trusted_workflows`
(REQ-032). Bets B, C and D (REQ-016..018) move to v0.5.0 unchanged.

Update, 2026-11-25: v0.5.0 is prepared with the `.planted` suffix (REQ-033)
and the lockfile pack in examples/locks (REQ-034); the owner holds the tag.
Bets B, C and D move to v0.6.0 unchanged. When the census (bet B) ships, its
number becomes a second O3 number in north-star.toml (owner, 2026-11-24).

The yardstick is pulseengine.eu's `data/north-star.toml`. A Fable planner
wrote the first draft. A second Fable agent then checked it cold, with only
the North Star and the draft in front of it. This version is revised from the
checker's findings, summarised at the end.

The cycle ends at the 2026.12 varve layer. Every date below is that layer
unless stated otherwise.

## Baseline (measured 2026-11-19, read-only GitHub API)

Scope: the 33 public, non-fork, non-archived repositories. Two private
repositories were not surveyed.

- **Required checks:** 117 required status contexts across 15 repositories,
  all from classic branch protection.
- **Manifests:** 7 repositories carry a `ci-controls.toml`, with 40 controls:
  sigil 15, plant 12, spar 6, rules_wasm_component 3, witness 2,
  bazel-file-ops-component 1, rules_rocq_rust 1. They run in four ways:
  - the released plant, verified by cosign and sha256 (sigil);
  - the plant action, built from a commit (witness);
  - a Python script (rules_wasm_component);
  - inline shell (rules_rocq_rust);
  - for spar and bazel-file-ops-component, unknown.
- **Binding:** a control's `check` key is free text, not bound to a required
  context. By exact name, at most 5 of the 117 contexts match a control's
  `check`. sigil's 15 controls say "fork guard", and its 2 required contexts
  have other names.
- **Report schema:** plant's run report has no schema name. Only
  `plant guard` has one (`plant.guard.v1`).

## Step 0: answer the unknowns that decide the shape (by 2026-11-26)

Each answer is recorded in the release tracking issue with the command or
message it came from. A "no" changes the plan as stated.

1. **kiln:** can kiln v0.8.0 run a wasip2 command component with a
   preopened directory, passing through its exit code and stdout? Test: a
   hello-world component that lists a directory. "No" drops bet D.
2. **Bundle verify:** does a single bundle verify command exist for the
   2026-Q4 O2 commitment, and who owns it? Ask the pulseengine.eu session. If
   it exists, bet C ranks above bet D; if not, bet C is dropped.
3. **Indicator ingestion:** how does pulseengine.eu ingest an indicator
   number (file, schema, schedule)? Ask the pulseengine.eu session. This
   shapes bet B's output, not whether it is built.
4. **Proof-carrying repositories:** which repositories carry proofs (Lean,
   Rocq, Verus, Kani), and is each one's proof check a required context?
   Answered by searching the organisation for their build files and reading
   branch protection. This is the denominator for bet A.

## Bet A: O3 proof-gate controls (rank 1)

**What.** Packs of planted escapes for proof checks, in `examples/proof/`.
For Lean, a `sorry` and an added `axiom`. For Kani, a `kani::assume` that
narrows a harness's input range. Rocq (`Admitted`, `Axiom`) and Verus
(`assume`, `external_body`) are a stretch. Each control must turn the proof
check, its axiom audit or its trust-escape ledger red. A ledger check needs a
base commit to compare against, so the manifest gains an optional key that
keeps a shallow `.git` in the scratch copy. That is an additive change to
seam #8, announced there before the tag.

**Objective and indicator.** O3, state `unmeasured`. Indicator, quoted:
"Proof-carrying repositories whose proof check, with a kernel axiom audit and
a trust-escape ledger, is a required check. The ledger counts every
assumption that narrows a harness's input range." Guard, quoted: "Ledger
entries, input-narrowing assumptions included, may only shrink." This bet
makes the indicator measurable per repository as three facts, each backed by
a planted control's verdict:
- proof check required and red on a planted hole;
- axiom audit red on a planted axiom;
- ledger red on a planted growth, input-narrowing assumes included.
It goes from no measurement to measured for the step-0 list.

**Acceptance, plant-owned:**
- For Lean and for Kani, the pack passes on a fixture proof in plant's CI,
  with the tool pinned. Every control has a regex, so a build error doesn't
  count as a rejection.
- For each of the two tools, a stand-in proof check that only type-checks
  (no axiom audit, no ledger) turns the axiom and assume controls FAIL-OPEN
  (same method as the sieve stand-in in v0.3.0).

**Acceptance, adoption (owner approval needed for each PR):**
- The three facts are measured and published for every repository on the
  step-0 list.
- At least one repository has all three facts "yes", each backed by a bound
  control.

**Kill.**
- The pack is wrong if any control reports PASS when the planted hole sits in
  a file the proof check does not build. The fixture includes such a file;
  that control must FAIL.
- The bet failed if, at the 2026.12 layer, the facts are not published for at
  least two of the step-0 repositories.
- In a consumer repository, a control that stays green is not "the pack
  worked". That repository's fact is recorded as "no", and the indicator does
  not count it.

**Dependencies.** The proof-carrying repositories (review and merge the
controls; building a missing audit or ledger is their work, not plant's), and
possibly rules_lean, rules_verus and rules_rocq_rust. Owner approval: PRs in
those repositories.

**Not claimed:** that any proof is sound, that an audit is complete, or that
"yes" on three facts means a repository is assessable.

## Bet B: required-check census, one verified runner (rank 2)

**What.** `plant census` is a pure function from files (each repository's
required contexts, workflows, manifest and CI report) to `plant.census.v1`.
It splits every required context into covered, declared-not-bound, aggregate
and uncovered. The run report gets a schema name, `plant.report.v1`. The
action installs the released plant by verifying its cosign bundle and sha256,
instead of building from source, and uploads the report as a CI artifact.

A context counts as covered only when all five hold:
1. **Bound:** the control names the context exactly, and its `run` is a
   whole command line of a step in the job that produces it.
2. **Red:** the planted run went red for its stated reason, with a regex.
3. **Green baseline:** the unplanted run passed; no `baseline = false`.
4. **Fresh:** the report is the artifact of a default-branch CI run in the
   current layer month.
5. **Verified:** the report came from a released plant, verified by cosign
   and sha256.

plant's own repository runs plant built from the commit under test, which is
the point of its self-controls. So plant is reported separately and is
neither in N nor in M.

**Objective and indicator.** This serves O3's summary ("each public claim …
maps to a CI check that can fail"). It is **not** the O3 indicator, which bet
A measures. N and M per repository is a number the North Star does not define
today. Whether it becomes a second O3 number in `north-star.toml` is the
owner's decision, asked in the morning notice. This plan does not assume it.

**Acceptance:**
- On a committed three-repository fixture, `plant census` matches a committed
  expected file byte for byte.
- Six planted controls in plant's manifest PASS, each turning the census red
  or its count down:
  - a report whose planted run exited 0, counted as covered;
  - a control whose `run` is not in the job;
  - a `baseline = false` control;
  - a stale report;
  - a report from an unverified runner;
  - an aggregate context counted as covered.
- Two planted controls turn the action's install red: a wrong checksum and a
  wrong certificate identity.
- At the 2026.12 layer, the census is published for at least 12 of the 14
  repositories with required checks (15 less plant), with no manual edits to
  its inputs.

**Kill.**
- The claim is false if a context listed as covered is green on its own
  planted input when re-run from a clean clone. At each layer, plant's CI
  re-runs one repository's manifest, chosen by layer id, and a mismatch fails
  the census.
- The binding rule is wrong if, after the authors of the 28 controls outside
  plant review them, fewer than 10 can be bound. Then it is redesigned before
  any number is published.

**Not doing:** filing an issue per uncovered context. Up to 112 unpicked
issues would worsen O4's "time from ready to first pick-up". The census lists
gaps; issues are filed only on the owner's decision.

**Dependencies:**
- pulseengine.eu: reads `plant.census.v1`. Ingestion comes from step 0, and a
  new seam is opened in plant.
- witness, rules_wasm_component, rules_rocq_rust, spar and
  bazel-file-ops-component: move to the verified action. These are PRs, each
  needing owner approval.
- Owner approval: a read-only token that can read branch protection
  org-wide; whether the two private repositories are in scope; and the first
  cross-repository re-run, on a hosted runner, from the default branch.

**Not claimed:** that a covered check is a good check, that an uncovered one
is fail-open, or that the census measures proofs.

## Bet C: bundle negative controls (rank 3; above D if step 0 finds the verify command)

**What.** O2's guard, quoted: "The verify command must fail when any piece of
evidence is removed (negative control in CI)". plant ships it as a pack for
the bundle: for each of the rivet trace, the witness report and the sigil
attestation, one control that removes it and one that alters it. That is six
controls against the real verify command at a pinned version.

**Objective and indicator.** O2, state `measured`. The indicator ("consumer
repositories whose latest release carries the full bundle and passes the
verify command") is not moved by plant. The bet makes O2's guard
demonstrable for the 2026-Q4 committed target, a wohl release with the full
bundle and one verify command.

**Acceptance:**
- All 6 controls PASS against the real command, each regex naming the
  missing or altered piece.
- A stand-in verify command that only checks that the bundle exists turns all
  6 FAIL-OPEN.
- Adoption, owner approval needed: the manifest merged in wohl and bound to a
  required context. wohl's current required contexts are unknown; they are
  read in step 0.

**Kill.**
- Dropped if step 0 finds no single verify command.
- If the real command stays green with a piece removed, O2's guard does not
  hold. That is reported to the command's owner, and the bet's acceptance has
  failed until it is fixed: a finding is not a pass.

**Dependencies:** the verify command's owner (step 0), wohl, and sigil's
release (the commitment needs it installable).

## Bet D: plant guard as a signed WASI component under kiln (rank 4; dropped if step 0 item 1 says no)

**Update 2026-11-27.** The owner approved bet D in an option dialogue. Done: plant
guard builds for wasm32-wasip2 behind `cfg(target_os = "wasi")`, with no split
into a separate crate. It exits 0/1/2 through std::process::exit, because
returning a nonzero ExitCode from main reaches the host as 1 (measured with
Rust 1.100; with 1.99.1 std::process::exit collapses too). CI job `guard (wasi)`
holds it equal to the native guard under wasmtime 50.0.2, and two planted controls
(`ci-controls.wasi.toml`) show that job can fail. Still open: kiln as an advisory
second runner (kiln 0.9 runs meld-fused wasip2 components, per pulseengine.eu on
2026-11-27, not yet measured here), and signing the component in the release.

**What.** Split plant into a pure core (manifest, verdicts, reports, guard,
census) and the native runner, which starts processes. Build the core for
wasm32-wasip2 and ship `plant guard` as a component that the chain builds and
signs and kiln runs. CI holds an equivalence test against the native
`plant guard`, which is the old version.

**Objective and indicator.** O5, state `unmeasured`. Indicator: tools and
gates running as signed WASI components under kiln, with wasmtime as the
differential, "out of all our tools and gates". The org-wide denominator
belongs to pulseengine.eu and is unknown here. plant's contribution is +1 in
the numerator: one gate, `plant guard`. The controls runner stays native and
is counted as not running as a component.

**Acceptance:**
- The core crate builds for wasm32-wasip2 with no `libc` or process code
  (`cargo tree -p plant-core` shows neither).
- A CI job runs native `plant guard`, the component under wasmtime and the
  component under kiln over every `tests/guard.rs` fixture plus spar's tree
  at a pinned commit. It requires identical exit codes and byte-identical
  `plant.guard.v1` (18 findings on spar).
- Planted controls PASS:
  - a core that skips one guard rule turns the equivalence job red;
  - a component with one byte changed fails signature verification.

**Kill.**
- If kiln cannot run the component with a preopened checkout by the 2026.12
  layer, the release ships it as a wasmtime-only differential, and no O5
  number is claimed.
- If a core dependency (clap, regex, toml, yaml-rust2, serde) does not build
  for wasm32-wasip2 in the first week, the bet is dropped for this cycle.

**Dependencies:**
- kiln (step 0).
- sigil/wsc for signing.
- meld and loom, if fusing or optimising applies; unknown.
- varve, to carry the component.
- Seam #14 gains a second artifact (notice before the tag).
- Owner approval: the component in release.yml's signed artifacts.

## Ranking and cuts

1. **A:** the only bet that measures the O3 indicator as written, and most of
   it is plant's own.
2. **B:** builds the census that A's facts and future bets are scored with.
   The verified install and the report upload are prerequisites for counting
   any repository.
3. **C:** tied to the only committed 2026-Q4 target. It moves above D if step
   0 finds the verify command.
4. **D:** self-contained up to kiln's capability, which step 0 tests first.

Cut order if the cycle runs short: D, if step 0 item 1 fails; then C, if no
verify command; then B's org-wide publishing, keeping the fixture-tested
census.

## What the checker changed

The cold check returned these findings; each is answered above.
- The census moved no defined indicator. It is now labelled as serving O3's
  summary, and whether it becomes an indicator is the owner's call.
- The proof pack measures the O3 indicator as written, so it is ranked first.
- Acceptance lines that could not fail were removed:
  - "plant 4 of 4, or the census names which";
  - M checked against its own input;
  - a `_GAP` grep;
  - an O4 "observation target".
- Plant-owned acceptance is now separate from adoption.
- A consumer's green control is recorded as a "no", not "the pack worked".
- The binding threshold was reset, from more than half of 40 to fewer than 10
  of the 28 controls outside plant.
- plant's own controls are excluded from N and M.
- The issue-per-gap filing was dropped, because it would worsen O4.
- The O3 guard is now quoted in full, including "input-narrowing assumptions
  included".
- relay's proofs are no longer assumed; the step-0 search answers that.
- The unsupported wohl claim was removed.
- The O5 denominator is no longer "3 plant commands".
- The unknowns are now step 0, with a date, before any build.
